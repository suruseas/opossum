> [!WARNING]
> **`COMPOSE_PROJECT_NAME`, `COMPOSE_FILE` and `COMPOSE_PROFILES` are now read, from the `.env` as well as from the shell, so a directory that sets one of them is a different project, a different file, or a different set of services than it was under v0.32.0.**
>
> **`COMPOSE_PROJECT_NAME` renames the project.** What an earlier opossum started in that directory stays under the old name — the compose file's `name:`, or the directory's — where `ps` no longer lists it and `down` no longer stops it. The next `up` starts the newly named project beside it, with named volumes that are empty; where a service publishes a host port the old project still holds, that `up` refuses instead (`[OPSM-201]`) and makes nothing. **No data is gone**: it is in the old project's volumes. opossum says all of this and names the way back — `opossum -p <old name> down` stops and removes the old containers, `-v` its volumes, and `--rmi local` the images it built.
>
> **`COMPOSE_FILE` chooses the compose file**, where opossum used to read whatever `compose.yaml` was in the directory. Where it names files in that same directory, what an earlier opossum started there is an orphan of the same project now: `opossum up` names it (`[OPSM-402]`) and `opossum down --remove-orphans` removes it. Where it names a file in another directory, the project is usually renamed too, and the paragraph above is what happens.
>
> **`COMPOSE_PROFILES` in the `.env` turns profiles on**, so the next `up` starts services it did not start before. And a run given `--profile` no longer adds a `COMPOSE_PROFILES` to it: the flag alone counts, as with docker compose.
>
> This is what docker compose does with these variables, and opossum ignored them. A directory that sets none of the three is unaffected.
