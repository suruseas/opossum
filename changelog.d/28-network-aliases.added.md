- On Apple `container` 1.6.0 and later, `up` gives a service its network aliases: `aliases: [cache]` under a network is passed as `cache.<project>.<domain>`, so other services in the project reach it as `cache`, as they reach a service by its name. The runtime does not keep names apart by network, so an alias is looked up from every network and resolves to its address on the network that writes it. An alias with a dot (`db.internal`), or one that is not a single DNS label, is not passed, and stays listed by `config` among the ignored fields; nor is one that is a service's name, one another service takes first, or a 33rd on one network. `up` says which aliases it left out and why (`OPSM-502`). A run the runtime refuses because a container it already has holds some of the aliases, such as one an earlier `up` left, is made again once without those, and `up` says which; a service whose own name another container holds as an alias gets the advice `OPSM-217`. Known difference: adding a service named after an alias another running or stopped service holds fails that `up` (`OPSM-217`) when the new service starts before the holder, where docker compose starts both; `opossum up --force-recreate <the service that held it>`, then `opossum up`, gets past it (`--remove-orphans` when the holder is a container the file no longer has). With no DNS domain, or an earlier runtime, no alias is passed, as before. A one-off `run` passes none, as `docker compose run` does without `--use-aliases`.
